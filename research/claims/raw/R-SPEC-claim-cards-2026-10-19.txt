## Five-line risk summary (biggest architectural risks found)

1. **SDK 1.x is a maintenance line**: pin `@modelcontextprotocol/sdk@1.32.1` exactly (supports spec through 2025-11-25 only); do not float `^1.32` expecting new features — URL elicitation and tasks are in 1.32.1, but the future is v2 packages (`@modelcontextprotocol/server`/`client`, spec 2026-07-28). *(CLM-005, 020)*
2. **-32042 is spec-defined, not invented** — good news for the blueprint — but the spec REQUIRES `data.elicitations[]` of URL-mode entries each with `elicitationId`, and forbids using it for anything else; a bare `-32042` with custom data will be non-conformant and unparseable by the SDK's `UrlElicitationRequiredError`. *(CLM-015, 016, 017)*
3. **URL-mode elicitation IS in SDK 1.32.1** (`elicitInput({mode:'url'})`, completion notifier, examples) — no hand-writing needed — but it is spec-flagged as volatile, and clients MUST show full URL + consent and MUST NOT auto-fetch; our UI must implement that flow, and secrets must never go through form mode. *(CLM-009, 016)*
4. **Tasks are experimental on both sides** (spec note + SDK `.experimental.tasks`, in-memory store is session-bound) — build the demo so the core loop degrades gracefully if task APIs shift; MRTR retry on `-32042` is a client-side responsibility, the SDK gives you only a typed error to catch. *(CLM-010, 017)*
5. **Origin validation is MUST in the spec but opt-in and `@deprecated` in the SDK server transport** — with no `allowedOrigins`/middleware configured we ship a DNS-rebinding hole; also remember 400-on-missing-header vs 404-on-dead-session semantics exactly as in CLM-001/003, and form elicitation is FLAT primitives only (no resource links, no nesting) — resource_link belongs to tool results only. *(CLM-003, 004, 007, 014, 018, 019)*
